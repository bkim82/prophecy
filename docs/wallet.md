# Wallet dashboard

- Status: canonical CDP smart-account identity, Deposit (receive), Send of ETH or any held Base ERC-20 (gas paid in USDC), and exact-input Swap/Buy of any Base token through CDP Swap (gas paid in ETH by the account), or both with free gas sponsored by CDP's Paymaster behind `NEXT_PUBLIC_WALLET_FREE_GAS=true`, built behind `WALLET_TRANSACTIONS_ENABLED` + `NEXT_PUBLIC_WALLET_TRANSACTIONS_ENABLED`. Card → USDC hosted Onramp is built behind `WALLET_ONRAMP_ENABLED` + `NEXT_PUBLIC_WALLET_ONRAMP_ENABLED`.
- `/wallet` requires application sign-in and reads the canonical Base smart-account address from `useAppAuth()` through `app/lib/useWalletConnection.ts:18`; no external-wallet connect, disconnect, switch-wallet, switch-chain, or owner-EOA display flow remains.
- Local dev (`NODE_ENV=development`) skips sign-in: a signed-out `/wallet` renders the dashboard with `MOCK_WALLET` + `mock` holdings/activity fixtures (`app/wallet/mockWallet.ts`, `app/wallet/page.tsx`); only balance/holdings/activity are faked, ETH/history/trending/search stay live. Send/Swap still hit the real intent routes and fail without a session.
- `app/lib/wallet.ts` contains display/Base helpers only. `@coinbase/wallet-sdk` is removed from `package.json`.
- `app/wallet/page.tsx`, `app/wallet/WalletDashboard.tsx`, `app/WalletDesk.tsx`, `app/BalancePill.tsx`, and `app/sanctum/SanctumView.tsx` use the session-derived smart account. Sanctum's preview balance/trading model is unchanged.
- Native balance is a public Base read through `GET /api/wallet/balance?address=` (`app/api/wallet/balance/route.ts:9`, `lib/alchemy.ts`); ERC-20 holdings remain `GET /api/wallet/holdings?address=`.
- Public onchain/market routes retain caller-supplied addresses because the data is public. When embedded auth is active, balance/holdings/activity/ETH/history/prices/search/trending/new reads use database-backed per-IP limits (`app/api/wallet/readLimit.ts`); prices/history reject anything but 0x addresses (history also `eth`) before they reach upstream URLs or caches.
- `GET /api/wallet/activity?address=` merges confirmed Alchemy activity with the signed-in canonical account's durable local intents (symbol + display amount from `curatedToken`, raw amount kept), skips unconfirmed `created` intents, and deduplicates confirmed transaction hashes (`app/api/wallet/activity/route.ts:13`).
- One overview page, no tabs (`app/wallet/WalletDashboard.tsx`): "Wallet" title + Base/address pill (copy, Basescan link), `BalanceCard.tsx` (available total blank until the first holdings + ETH read; sub-line = single asset qty or asset count; Deposit, Withdraw = `SendSheet`, ⋯ menu = Swap tokens / Explore tokens / Sign out; stats = 24h change (sub-cent moves neutral), Network fees = free-gas flag, right-aligned tinted chips in the same row: Gas = ETH balance in USD, Cash = USDC balance; each opens `CoinDetailPanel.tsx` when held), Holdings (+ Explore tokens link), Recent activity (4 rows + View all), three trust cards, footnote linking the address on Basescan. Copy states only what's true: Arena stakes are Embers, so no "in open matches" figure.
- Holdings: `CoinList.tsx`, every coin except USDC (header strip = total of unhidden holdings + token count + Sort by Value/Name/24h change; Asset / Price / Balance; search only above 6 coins; empty state links to Explore tokens); each `CoinRow.tsx` has a ⋯ menu to Hide/Unhide the coin (per-browser localStorage `wd-hidden-coins-v1`, `app/wallet/hiddenCoins.ts`); hidden coins drop out of the list (a "Show hidden (n)" toggle reveals them dimmed) and the balance total/24h change, but stay in Send/Swap pickers. A row opens `CoinDetailPanel.tsx`; `useWalletHistory.ts` backs detail charts.
- Activity: one `useWalletActivity` poll (`app/wallet/ActivityList.tsx`) feeds both Recent activity and the View all list (30s visible-only poll, 15s while a local intent is `submitted`, 10s during a deposit watch; calls `POST /api/wallet/reconcile` first and refreshes holdings when one reaches `included`). Rows: received = Deposit, sent = Withdrawal, swapped = Swap; absolute date · status (chain rows Confirmed); Basescan link only for real tx hashes. Explore tokens view: shared `TokenExplorer.tsx` + `AdvancedTokenDetail.tsx` (`AdvancedTab.tsx`).
- Deposit ("Add funds", `DepositSheet`, `app/wallet/ActionSheets.tsx:39`): Card or Apple Pay | Transfer USDC switch (card side only with Onramp on), static USDC/Base tiles, QR of the plain address (`app/wallet/QrCode.tsx`, `uqr`, ECC M), address in 4-char groups with first/last bold + Copy, Base-only warning, gas note, "No minimum deposit · Network fee paid by sender".
- Deposit watch (`WalletDashboard.tsx`): opening Deposit baselines the incoming chain transfer hashes; the first new `received` row within 15 min is the arrival — the sheet flips to "Received …", holdings reload, `wallet-updated` fires, and with the sheet closed a toast shows for 8s. Only while `/wallet` stays open.
- Buy USDC with card (`BuyWithCard`, `app/wallet/ActionSheets.tsx:116`; shown when `NEXT_PUBLIC_WALLET_ONRAMP_ENABLED=true`): optional USD amount → `POST /api/wallet/onramp` (`app/api/wallet/onramp/route.ts:23`; 503 unless `WALLET_ONRAMP_ENABLED=true`, 6/min, amount `^\d{1,6}(\.\d{1,2})?$` > 0) → `createUsdcOnrampSession` (`lib/onramp.ts`) fixes destination = viewer smart account, network `base`, asset `USDC`, `paymentCurrency: USD`, `redirectUrl` = `APP_ORIGIN`/wallet, `partnerUserRef` = user id (`sandbox-` prefixed when `WALLET_ONRAMP_SANDBOX=true`); client body fields beyond `amount` are ignored. `createCdpOnrampSession` (`lib/cdp.ts:58`) signs a JWT with `@coinbase/cdp-sdk/auth` and calls `POST /platform/v2/onramp/sessions` (CdpClient has no Onramp); only a `https://pay.coinbase.com/` URL is returned. The tab opens on click (popup-safe) then navigates. Coinbase shows quote/fees/limits/eligibility; the app promises none.
- Each session inserts an `onramp_orders` row (`status: created`, URL not stored, single-use) + `onramp.session_created` audit event. No order status tracking/webhook yet: rows never leave `created`; purchased USDC shows up through normal holdings/activity reads.
- Send moves native ETH or any Base ERC-20 the account holds. The server resolves the token (`resolveSendToken`, `lib/transactionIntents.ts`): curated ETH/USDC carry per-send/daily caps (`app/lib/embeddedWallet/tokens.ts`); other ERC-20s use Alchemy decimals and are bounded only by balance. Decimal input is converted directly to raw `bigint`; the batch is exactly `USDC.approve(CDP_ERC20_PAYMASTER, GAS_ALLOWANCE_RAW)` + one native transfer or `token.transfer(recipient, amount)`, or the transfer alone when free gas is on (`buildSendIntent(..., freeGas)`, `isSponsoredSend`), encoded and independently decoded; self/zero/mismatched-token/over-limit/other-batch calls fail closed (`app/lib/embeddedWallet/intents.ts`).
- Recipient field accepts `@handle`/display-name search over other users with a handle and an active Base smart account (`GET /api/wallet/recipients?q=`, `app/api/wallet/recipients/route.ts`), labelled only by unique `@handle` (2+ chars; never returns addresses), or a pasted 0x address. A picked handle is sent as `recipientHandle` instead of `recipient` (exactly one, else 400) and resolved only server-side (`walletAddressForHandle`, `lib/profile.ts`); no active wallet returns 409 (`app/api/wallet/intents/route.ts`). Review shows @handle plus the server-resolved address, so handle→address is not secret: each lookup costs one rate-limited (12/min), audited intent.
- Send preparation creates an idempotent `transaction_intents` row; `POST /api/wallet/intents` returns `{ intent, token }` and the review renders only those server values (amount via `formatUnits(inputAmount, token.decimals)`, `intent.recipient`, contract address for non-ETH/USDC tokens). `confirm` is called only by the review's Confirm button (`useConfirmThenSubmit`, `app/wallet/ActionSheets.tsx:179`; `app/api/wallet/intents/[id]/confirm/route.ts`), for both Send and Swap; a swap's confirm body carries the reviewed raw `minimumOutputAmount` (stored on the row, `confirmTransactionIntent` `lib/transactionIntents.ts:187`), a send's must not. Back or closing the sheet on a review cancels the unclaimed intent (`POST /api/wallet/intents/[id]/cancel`, `cancelTransactionIntent` `lib/transactionIntents.ts:213`, `user-canceled`); reconciliation still cancels `confirmed_by_user` rows older than 15 min (`confirmation-abandoned`). From the claim onward a failure throws `ClaimedIntentError` (`sign.ts:30`) and the sheet returns to the form instead of offering a retry that would 409; its `mayHaveSubmitted` is false for a refused claim or failed row check (the submit route's 409 names the reason: expired/used, call mismatch, daily limit) and only then is the user told the attempt may still land. A failed `reportBroadcast` after CDP returned a hash is retried 3×, then kept in localStorage and re-reported before the next reconcile (`client.ts`); `recordUserOperationHash` (`lib/transactionIntents.ts:326`) revives a `dropped`/`submission-interrupted` row to `submitted` for that late report.
- Only `app/lib/embeddedWallet/sign.ts` imports CDP send/swap APIs: elsewhere `@coinbase/cdp-core` and all `@coinbase/cdp-*/*` subpaths are banned and `cdp-hooks`/`cdp-react` are allowlisted to auth/read-only names (`eslint.config.mjs:5`). `useVerifiedSmartAccount` (`sign.ts:52`) rechecks browser user and exactly one smart account against the application session; the submit hooks then validate final calls, claim the intent, and report the user-operation hash.
- Wallet routes: no live app session (`getViewer()` null: revoked by a sign-in elsewhere, idle/absolute expiry, overwritten cookie) → 401 `{ code: "signed-out" }` (`walletSignedOut`, `app/api/wallet/responses.ts`); signed in without a smart account (Clerk mode) → 403 (`walletAccountRequired`). `jsonRequest` (`app/lib/embeddedWallet/client.ts`) dispatches `WALLET_SIGNED_OUT_EVENT` on that 401 and `CdpAuthBridge` signs the browser out (`app/auth/AuthProvider.tsx`); it never re-exchanges the CDP token silently, so "sign out everywhere" holds.
- Submission requires `WALLET_TRANSACTIONS_ENABLED=true`; the browser gate additionally requires `NEXT_PUBLIC_WALLET_TRANSACTIONS_ENABLED=true`. Gas is paid in USDC via CDP's ERC-20 paymaster: `useCdpPaymaster: true` + `paymasterContext: { erc20: USDC }` (`app/lib/embeddedWallet/sign.ts:132`); the account needs USDC for gas even when sending another token. Free gas (`walletFreeGasEnabled`, `app/lib/embeddedWallet/config.ts:18`; read by the server's `createSendIntent` and the browser) drops the approval and sends `useCdpPaymaster: true` with no `paymasterContext`, so the CDP project pays; the signer picks the mode from the stored batch shape, so intents created before a flip still sign; a Portal contract allowlist would block non-USDC sends. No custom paymaster proxy exists.
- `lib/transactionIntents.ts` owns idempotency, guarded status transitions, call hashes, per-token UTC-day sponsored-spend counters, audit events, and bounded reconciliation. `POST /api/wallet/reconcile` maps CDP complete/failed/dropped results to local terminal states and leaves transient provider failures pending.
- Transaction vocabulary: `created | confirmed_by_user | submitted | included | reverted | dropped | replaced | canceled`; submitted is displayed as pending, never success.
- Swap (`SwapSheet`, `app/wallet/ActionSheets.tsx`): Buy/Sell on a holding's detail panel or an Explore-tokens market token opens it preset (`openBuy`/`openSell`, `app/wallet/WalletDashboard.tsx`); pay with any held coin (Explore tokens' Sell is enabled for any held token; holding addresses are lowercased in `WalletDashboard.tsx` to match market addresses); receive any held coin, the market token, USDC, ETH, or any Base token found by `TokenSearchField` (hidden on an Explore-tokens Buy, which passes `extraToken`; `/api/wallet/search` by name/ticker/contract; a pasted contract with no listed pool is still pickable and resolved server-side on review). Typing shows a rough USD-price estimate only.
- Review swap creates a `kind: "swap"` intent (`createSwapIntent`, `lib/transactionIntents.ts`; `POST /api/wallet/intents`): both tokens resolved server-side via `resolveSendToken`, recipient = the account, `calls = []` because CDP builds the swap calls, curated ETH/USDC per-trade caps apply, daily caps reserved at claim for both kinds. Review shows CDP's live quote (`useSwapQuote` → `useGetSwapPrice`): expected and minimum output, 1% slippage (`SWAP_SLIPPAGE_BPS`, `app/lib/embeddedWallet/tokens.ts`), gas in ETH with CDP's `totalNetworkFee` estimate, contract addresses under non-ETH/USDC symbols. Review/Confirm are disabled with no ETH balance, or when an ETH sell plus fee would use the whole balance (display-number guard only); free gas skips both guards and shows gas as free.
- Confirm (`useSubmitSwapIntent`, `app/lib/embeddedWallet/sign.ts:168`): before claiming, `getSwapPrice` preflight (route, balance; an allowance issue must name Permit2 and never ETH); if needed, `token.approve(PERMIT2, exactAmount)` as its own self-paid user op, awaited via `getUserOperation` until `complete` (90s; failed/dropped throws), then re-quoted until CDP sees the allowance (15s); then sizes `executeSwap`'s `slippageBps` from the fresh quote's `toAmount` so its minimum stays ≥ the confirmed `minimumOutputAmount` (`executionSlippageBps`, `app/lib/embeddedWallet/intents.ts`; capped at 1%), refusing with < 10 bps of room. These failures leave the intent confirmed and retryable with no daily-cap reservation. Only then claim → `executeSwap({ slippageBps, useCdpPaymaster: freeGas, idempotencyKey: intent.id })` (the Permit2 approval op takes the same `useCdpPaymaster`) (CDP quotes, signs Permit2, simulates, submits) → report the user-op hash. CDP re-quotes inside `executeSwap`, so the floor holds up to one request's drift.
- Reconciliation bounds a reported swap op (`assertSwapOperationCalls`, `app/lib/embeddedWallet/intents.ts`): native value ≤ ETH sold (0 for ERC-20 sells), no top-level `transfer` of the sold token, any top-level `approve` of it only to Permit2 for ≤ the amount; otherwise `dropped`/`provider-call-mismatch`. The router is not pinned, so a swap's `included` status is still largely client-attested — don't use it for rewards.
- Without free gas no swap path uses the Paymaster: swap and approval gas come from the account's ETH (Deposit sheet says so; with free gas it says Prophecy covers gas). Activity shows a pending swap as `FROM → TO symbol` with no "To" line.
- No cost basis: average entry and total return are not inferred from current holdings.
